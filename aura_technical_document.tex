\begin{abstract}
A stolen password is no longer the hard part of an account takeover. Credential harvesting kits, session-riding malware, and cookie-replay tooling are commodity products on the underground market, and once an attacker holds a live session token, traditional login-time defenses such as passwords, device fingerprints, and one-time MFA codes have nothing left to check. The fraud has already moved past the door they were guarding. This paper presents \textbf{AURA}, a real-time behavioral biometric security platform built to protect the Central Bank of India's customer portal at the point where most defenses go dark, the authenticated session itself. AURA fuses high-frequency client-side keyboard and mouse dynamics with a deep Convolutional Neural Network, \textbf{VarCNN}, running in a server-side inference pipeline that continuously asks whether the hands on the keyboard still belong to the enrolled customer. When confidence drops, a four-tier containment architecture responds proportionally, rotating AES-256 session keys, tightening transaction limits, sliding session timers on a 10-minute inactivity window, and isolating credentials per browser tab through header-scoped \texttt{sessionStorage} bindings. We describe the architecture, protocol, and data design of our proof-of-concept implementation and demonstrate that VarCNN reaches 98.1\% detection accuracy at the 64-event telemetry buffer size used in production.
\end{abstract}

\section{Introduction \& Problem Statement}
Internet banking security has historically been a story about the front door. Username and password combinations, device fingerprints, and multi-factor authentication tokens all answer one question, and only one question: is this the right person logging in right now. They are silent for the rest of the session. Once an attacker steals a customer's session cookie or compromises their browser through session-riding malware, they inherit everything the legitimate user could do, and no checkpoint downstream is watching for the switch.

\begin{threatbox}{Threat Scenario}
A customer's laptop is infected with an infostealer that exfiltrates browser cookies. Hours later, on the other side of the country, an attacker loads the stolen session cookie into their own browser and lands directly inside the customer's authenticated banking dashboard, no password, no OTP, no fingerprint check required. Every static defense the bank deployed at login has already done its job and stepped aside. From this point forward, only behavior can tell the two users apart.
\end{threatbox}

A second, quieter vulnerability compounds the first. Conventional banking portals rely on browser-wide cookies for session persistence, and the browser dutifully attaches that cookie to every outgoing request from every open tab. A malicious script running in one tab inherits the authenticated session of every other tab the moment it makes a request, opening the door to Cross-Site Request Forgery and tab-level session hijacking without ever touching the original credentials.

Taken together, these gaps define what the Central Bank of India needs from a session-layer defense. The system must:
\begin{enumerate}
    \item \textbf{Continuously verify identity} after login, using implicit behavioral signals such as typing tempo and mouse movement velocity that an attacker cannot simply copy alongside a stolen cookie.
    \item \textbf{Isolate session credentials} across browser tabs so that compromise in one tab cannot silently propagate to another.
    \item \textbf{Minimize the window of exposure} for sessions left idle, without punishing customers who are actively, if slowly, working through a transaction.
    \item \textbf{Contain threats in real time} through graduated verification rather than blunt, permanent account locking that turns every false alarm into a support ticket.
\end{enumerate}

\section{Proposed Solution}
AURA answers each of these requirements with a single design principle: trust is not binary, and neither is the bank's response to losing it. Every authenticated session carries a continuously updated risk score between 0 and 1, and that score drives a four-tier containment architecture that escalates enforcement smoothly rather than snapping from "trusted" to "locked out."

\begin{itemize}
    \item \textbf{Tier 1, Protected} (risk score below 0.40). Behavior matches the enrolled profile. Standard transactions proceed, and every API call is encrypted under the currently negotiated AES-GCM session key.
    \item \textbf{Tier 2, Monitoring} (0.40 to 0.70). Minor behavioral drift is detected. AURA silently inserts a step-up OTP challenge without disrupting the interface the customer is already using.
    \item \textbf{Tier 3, Restricted} (0.70 to 0.90). The behavioral fingerprint diverges enough to suggest a likely account takeover in progress. Transaction limits tighten, the session key is rotated mid-session, and a physical step-up verification is required before any further high-risk action.
    \item \textbf{Tier 4, Contained} (0.90 and above). The system treats the session as compromised and deactivates it immediately, \texttt{is\_active = False}, cutting access to every banking API. Recovery requires an OTP plus coordinates from the customer's physical or downloaded \textbf{Cryptographic Recovery Card}, an out-of-band channel an attacker holding only the session cookie cannot satisfy.
\end{itemize}

\section{System Architecture}
AURA’s architecture is organized into three cooperating planes: a Client Telemetry Plane, a Four-Surface API Gateway & Cryptography Plane, and an AI/ML Decision Engine. To ensure absolute data hygiene and prevent cross-contamination, the API Gateway is split into four strictly isolated FastAPIs running on different ports: Customer (Banking workflows), Admin (SOC Dashboard), Attacker (Threat Simulation), and Showcase (Public Model Reporting). Each surface enforces strict CORS boundaries and its own authentication model. The three planes share a feedback loop: Telemetry flows in from the Customer browser, a fused risk score flows out of the engine, and that score immediately reshapes how the gateway treats the next request—including retiring the AES key the client just used to encrypt it.

\section{Workflow \& Protocol Handshake}
Behavioral telemetry, keystrokes and mouse positions, is captured client-side at high frequency and never sent raw or unencrypted. The protocol sequence runs as follows.
\begin{enumerate}
    \item Telemetry events accumulate in a local buffer. Once it holds 64 events, the buffer is encrypted under the current session key and shipped to the \texttt{/customer/telemetry} endpoint.
    \item The backend decrypts the payload and persists it.
    \item When the customer attempts a high-risk operation, such as adding a recipient or transferring funds, the system pulls recent telemetry and runs it through VarCNN.
    \item If the resulting threat score escalates the session's tier, the backend triggers key rotation inline. The response carrying the verdict is itself encrypted under the \emph{old} key, but its payload contains the \emph{new} session key and key version. The client decrypts that response, adopts the new key, and signs every subsequent request with it.
\end{enumerate}

This last step is the part worth dwelling on. The rotation hands the client a new key using a channel encrypted with the key it is about to retire, so even a passive observer who is logging encrypted traffic learns nothing about $K_{v2}$ before the legitimate client does. \section{AI/ML Model (VarCNN)}
VarCNN is the part of AURA that has to answer a deceptively hard question continuously and silently, namely whether the person typing right now still moves like the person who enrolled. It works from two complementary input vectors.
\begin{itemize}
    \item \textbf{Timing Sequence}: a $1 \times 1 \times 1024$ tensor of inter-event time intervals, capturing the rhythm of typing and clicking rather than its content.
    \item \textbf{Metadata Vector}: a $1 \times 10$ tensor of statistical summaries of mouse dynamics, including mean velocity, acceleration, and click frequency.
\end{itemize}

The timing sequence passes through five 1D convolutional layers, then a Global Average Pooling layer collapses the result into a 512-dimensional behavioral embedding. That embedding is compared to the customer's enrolled profile by cosine similarity, and the risk score climbs whenever the similarity drops below a calibrated threshold, exactly the kind of subtle drift a stolen cookie cannot fake.

Buffer size is the main lever on detection quality, and Fig.~\ref{fig:accuracy} shows why AURA settled on 64 events rather than going smaller for speed or larger for confidence.

\subsection{The Multi-Provider Risk Engine}
While VarCNN secures the continuous behavioral dimension, a stolen session often involves discrete high-risk actions like fraudulent transfers or navigating to phishing links. To cover the full attack surface, AURA's Risk Engine fuses outputs from six distinct intelligence providers:

\begin{enumerate}
    \item \textbf{TransactionRiskProvider}: An XGBoost/LightGBM model trained on the Feedzai BAF dataset, scoring the fraud likelihood of transfer amounts and beneficiary novelty.
    \item \textbf{SocialEngineeringRiskProvider}: An XGBoost model performing lexical analysis on URLs to detect phishing intent.
    \item \textbf{AccountTakeoverProvider}: A Random Forest classifier analyzing CMU Keystroke timing features (dwell, flight, and rhythm).
    \item \textbf{BeaconBehavioralProvider}: The VarCNN model handling continuous mouse and keyboard trajectory embeddings.
    \item \textbf{Network \& Device Trust Providers}: Heuristics tracking impossible-travel, VPN usage, and rooted devices.
\end{enumerate}

The Risk Engine applies contextual weight scaling (e.g., emphasizing Transaction Risk when a new payee is added) and uses attack-chain correlation thresholds to aggressively escalate risk if a LURE stage (phishing) is followed by a MONETIZE stage (transfer).

\subsection{ARIA \& Explainability}
To assist human Security Operations Center (SOC) analysts, AURA includes the Autonomous Risk Intelligence Agent (ARIA). Running as a continuous background asynchronous loop, ARIA scans recent \texttt{security\_events} and clusters anomalous behavior by user session. 

When a threat cluster breaches a confidence threshold, ARIA extracts the raw feature arrays and utilizes SHAP (SHapley Additive exPlanations) to generate visual bar charts of the feature contributions pushing the risk score up or down. These visual charts, alongside a timeline of the user's actions, are passed to a Vision Language Model (Qwen3.5-0.8B). The VLM acts as an automated L1 analyst, outputting a synthesized, natural-language threat assessment detailing the suspected attack vector (e.g., 'Account takeover followed by fraudulent transfer to a new beneficiary'). This drastically reduces the time-to-comprehension for human operators managing Tier-3 and Tier-4 containment events.

\section{Scalability, Limitations, \& Future Enhancements}
A proof of concept earns its credibility partly by being honest about where it still falls short. We see three areas that matter most before AURA could move beyond a hackathon build.

\subsection{Assumptions}
AURA assumes the client's browser supports modern Web APIs, specifically the standard Crypto Web API for local AES-GCM decryption, and that keyboard and mouse telemetry can be captured with millisecond precision. Both hold comfortably for current desktop browsers.

\subsection{Limitations}
\begin{itemize}
    \item \textbf{Device Variation}: a behavioral profile built on a desktop does not transfer to a touchscreen. Switching devices requires a separate enrollment, since mouse dynamics and touch dynamics are not the same signal wearing different clothes.
    \item \textbf{Cold Start}: a newly registered customer has no behavioral history to compare against. AURA defaults new accounts to Tier 2 monitoring for an initial training period of 64 telemetry events (keystrokes and mouse movements) until a reliable behavioral embedding can be established.
\end{itemize}

\subsection{Future Enhancements}
\begin{itemize}
    \item \textbf{Federated Learning}: train model updates locally in the browser rather than transmitting raw keystroke timing data to the server, narrowing what ever has to leave the customer's device.
    \item \textbf{Mobile Sensor Integration}: extend the behavioral signal to gyroscope, accelerometer, and pressure readings, sensors a mobile banking app has access to that a desktop browser never will.
\end{itemize}

\section{Conclusion}
AURA treats the authenticated session as the asset worth defending, not just the login screen in front of it. Behavioral biometrics catch what static checkpoints structurally cannot see, dynamic key rotation makes a stolen session key a depreciating asset rather than a permanent one, and tab-isolated storage stops one compromised tab from becoming an entire compromised account. The result is a security posture that escalates with evidence instead of jumping straight to a lockout, which is, in the end, the difference between a bank that merely reacts to fraud and one that contains it as it happens.
